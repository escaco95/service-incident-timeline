# Service Timeline

서비스의 장애·점검·불안정 기록을 캘린더와 하루 타임라인으로 관리하는 웹앱입니다.

캘린더 배지의 밝은 영역은 날짜별 이벤트 진행 시간, 어두운 영역은 시작 전·종료 후를 나타냅니다. 배지만 보고도 하루 중 발생 시점과 지속 시간을 대략 파악할 수 있습니다.

**빌드 없음 · 외부 npm 의존성 없음 · CDN 요청 없음 · 암호화된 JSON 저장**

## 실행

Node.js **22.13 이상**이 필요합니다. 이 프로젝트는 Node.js 24.13.1에서 검증했습니다. Node.js 런타임은 서버에 미리 준비합니다.

```sh
node server.mjs
```

브라우저에서 <http://127.0.0.1:8787>에 접속해 최초 암호화 비밀번호를 설정합니다. `npm install`, `npm run build`, Docker는 필요하지 않습니다. 운영 기록은 기본적으로 `data/store.json`에 생성되며 저장소에 커밋하지 않습니다.

## 브랜딩 설정

로그인한 뒤 상단 **설정 → 브랜딩 설정**에서 서비스 이름, 부제와 표시 여부, 기본 테마, 표시 시간대를 편집하고 저장할 수 있습니다. 저장하면 현재 화면과 서버에 즉시 반영되며 서버 재시작은 필요하지 않습니다. 다른 열려 있는 화면은 새로고침하면 새 설정을 적용합니다. 공유 비밀번호로 로그인한 사용자는 모두 이 공통 설정을 편집할 수 있습니다.

설정은 기존 `branding.json` 또는 `BRANDING_FILE`이 가리키는 파일에 저장합니다. 파일이 없으면 처음 저장할 때 생성합니다. 저장 시 입력값을 검증하고, 동시에 편집한 설정이 있으면 덮어쓰지 않고 최신 설정을 다시 불러오도록 안내합니다. 부제를 숨겨도 입력한 문구는 보존됩니다.

파일로 직접 관리하려면 [`branding.example.json`](branding.example.json)을 `branding.json`으로 복사해 수정할 수도 있습니다. `branding.json`은 `.gitignore`에 포함되어 각 환경에서 따로 관리합니다.

파일이 없으면 **이름 `Service Timeline`, 부제 `서비스 운영 기록`, 부제 표시 활성화, 라이트 모드, UTC 시간대**가 기본으로 적용됩니다. 별도 설정 파일 없이도 바로 실행할 수 있습니다.

```json
{
  "name": "Payment Timeline",
  "subtitle": "결제 서비스 운영 기록",
  "showSubtitle": true,
  "defaultTheme": "light",
  "timezone": "Asia/Seoul"
}
```

저장한 이름과 부제는 다음 위치에 반영됩니다.

- 로그인 화면과 앱 최상단의 도구 이름·부제
- 브라우저 탭 제목
- 로그인 화면 하단의 도구 이름
- 서버 시작 시 콘솔에 출력하는 서비스 이름

`name`은 1~64자, `subtitle`은 80자 이내입니다. **`showSubtitle: false`로 설정하면 부제 문구를 파일에 유지하면서 로그인 화면·앱 최상단·브라우저 탭에서 숨길 수 있습니다.** 다시 표시하려면 `true`로 바꿉니다. 옵션을 생략하면 기본값은 `true`이며, `subtitle` 자체가 빈 문자열이거나 생략된 경우에도 부제를 표시하지 않습니다. `showSubtitle`은 문자열이 아닌 JSON boolean(`true`/`false`)으로 입력합니다.

`defaultTheme`은 첫 방문 시 적용할 모드로 `"light"` 또는 `"dark"`를 지정합니다. 이 필드를 생략하면 `"light"`입니다. 로그인 화면과 앱 상단의 모드 버튼으로 언제든 전환할 수 있으며 캘린더, 타임라인, 입력·상세 팝업에 함께 적용됩니다.

사용자의 선택은 **해당 브라우저의 localStorage에만 저장**하며 서버로 전송하거나 이벤트 JSON에 저장하지 않습니다. 적용 순서는 **브라우저에 저장된 선택 → 브랜딩의 `defaultTheme` → `"light"`**입니다. 기본값만 적용받은 방문자는 선택값을 저장하지 않으므로 이후 브랜딩 초기값 변경도 반영됩니다. 직접 선택한 모드는 새로고침·로그아웃 후에도 유지하며 같은 사이트의 다른 탭에도 반영합니다. 브라우저 데이터가 삭제되면 브랜딩 초기값으로 돌아갑니다. 브라우저가 저장소 사용을 차단한 경우에도 현재 페이지에서 전환할 수 있지만 재방문 시에는 초기값을 사용합니다.

`timezone`에는 `"UTC"`, `"Asia/Seoul"`, `"America/New_York"` 같은 IANA 시간대 이름을 지정합니다. **필드를 생략하면 `"UTC"`**입니다. 날짜별 이벤트 구분, 오늘 표시, 월별 집계, 타임라인과 현재 시각, 이벤트 입력·편집·상세 시각에 공통으로 적용합니다. 모든 사용자가 같은 시간대를 사용하며 브라우저·서버의 OS 시간대와 무관합니다. 빈 문자열이나 잘못된 시간대 이름은 설정 오류로 처리합니다.

파일을 직접 수정했다면 서버를 재시작하거나 웹 설정 창에서 최신 설정을 불러온 뒤 브라우저를 새로고침합니다. 시간대를 바꾸면 기존 이벤트도 새 시간대로 표시하며 저장된 UTC 시각은 유지합니다. 빌드나 패키지 설치는 필요하지 않습니다. 파일 전체가 없을 때는 내장 기본 설정을 사용합니다. 기존 파일의 JSON 형식이나 필드 값이 잘못되거나 파일을 읽을 권한이 없으면 서버가 설명과 함께 시작을 중단합니다.

로그인 전에도 읽을 수 있는 **공개 이름·부제·초기 테마·시간대**이므로 이 파일은 평문으로 관리합니다. 비밀번호·API 키 같은 비밀 정보는 넣지 마세요. 이름은 암호화 키 도출이나 저장 파일 식별에 사용하지 않으므로 이름을 바꿔도 기존 이벤트를 같은 비밀번호로 열 수 있습니다. 서버 재시작 후에는 다시 로그인해야 합니다.

서버의 별도 파일을 사용하려면 환경 변수 `BRANDING_FILE`을 지정할 수 있습니다. 이 경로에 파일이 없는 경우에도 같은 기본값을 적용합니다.

```dotenv
BRANDING_FILE=/var/lib/service-timeline/branding.json
```

`branding.json`은 Git 배포에 포함되지 않습니다. 위처럼 릴리스 디렉터리 밖의 경로를 지정하면 재배포해도 설정이 유지됩니다. **웹에서 저장하려면 앱 실행 계정에 설정 파일과 상위 폴더의 읽기·쓰기 권한이 필요합니다.** 임시 파일을 쓴 뒤 교체하므로 폴더 쓰기 권한도 필요하며, 저장에 실패하면 기존 설정을 보존합니다. systemd 예제는 `/var/lib/service-timeline`에 쓰기를 허용합니다. 자세한 절차는 [배포 문서](docs/deployment.md)를 참고하세요.

## 서버 환경 설정

설정을 바꾸려면 `.env.example`을 `.env`로 복사하고 실행합니다.

```sh
node --env-file=.env server.mjs
```

| 환경 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | 수신 주소. 모든 IPv4 네트워크 인터페이스에서 연결을 받으려면 `0.0.0.0`으로 설정 |
| `PORT` | `8787` | HTTP/HTTPS 포트 |
| `DATA_DIR` | 프로젝트의 `data` | 암호화된 데이터와 직전 백업 저장 경로. 운영 시 소스 디렉터리 밖 절대 경로 권장 |
| `BRANDING_FILE` | 프로젝트의 `branding.json` | 브랜딩 설정을 읽고 저장하는 JSON 파일 경로. 파일이 없으면 기본값 적용 |
| `PUBLIC_ORIGIN` | 요청 주소 | reverse proxy 사용 시 실제 접속 주소. 예: `https://timeline.example.com` |
| `COOKIE_SECURE` | 자체 HTTPS에서 활성화 | HTTPS reverse proxy 사용 시 `true` |
| `TLS_CERT`, `TLS_KEY` | 없음 | Node.js에서 직접 HTTPS를 제공할 경우 인증서 파일 경로 |

공유 서버 운영에서는 HTTPS reverse proxy 또는 `TLS_CERT`/`TLS_KEY`를 사용하세요. `PUBLIC_ORIGIN`에는 실제 브라우저 접속 주소의 프로토콜·호스트·포트를 지정하며 경로는 포함하지 않습니다. Node.js 및 OS 업데이트는 별도 운영 항목입니다.

## 1차 기능

- 최상단 캘린더 / 타임라인 보기 전환
- 다크 / 라이트 모드 전환, 브랜딩 초기값과 브라우저별 선택 유지
- 캘린더 년도 직접 입력·좌우 이동, 월 선택·좌우 이동, 오늘로 이동
- 주말 빨간색 표시, 장애 적색·점검/불안정 노란색 배지
- 여러 날에 걸친 이벤트의 연속 막대, 종료 시각 미정 `∞` 표시
- 날짜 배경에 해당 날짜와 겹치는 가장 중대한 이벤트 반영
- 월에 필요한 4~6주만 표시하고, 화면 높이에 맞춰 날짜 칸 크기를 조절
- 화면 높이에 따라 주간 표시 레인 1~3개, 초과한 이벤트는 `+N 더 보기` 목록 팝업
- 배지의 **클릭한 날짜** 목록 팝업에서 해당 이벤트 강조, 목록 항목 클릭으로 타임라인 이동
- 하루 00:00~23:59 시간 축, 현재 시각 세로줄, 날짜 이동
- 좌우 연속 스크롤: 가까운 7일만 화면에 유지하며 날짜 범위를 이동
- 수동 이벤트 추가·상세 조회·편집·삭제, 유형 필터
- 최초 비밀번호 설정, 로그인·로그아웃, 8시간 세션
- 20초 간격으로 다른 화면에서 변경한 기록 반영

캘린더의 날짜 숫자, 이벤트 배지, `+N 더 보기`를 누르면 해당 날짜의 이벤트 목록 팝업을 엽니다. 배지로 열면 클릭한 이벤트를 강조하고, 목록 항목을 누르면 그 날짜의 타임라인으로 이동해 해당 이벤트를 강조합니다. 날짜 칸의 빈 영역에서는 새 이벤트를 추가할 수 있으며, 이벤트가 없는 날짜의 팝업에서도 추가할 수 있습니다. 목록 팝업에서는 이벤트의 시작·종료를 따로 표시합니다. 조회 날짜와 같으면 `당일 10:00`, 다른 날짜이면 `2026.09.08 23:00`처럼 연월일도 표시합니다. 종료 시각 미정 이벤트도 시작 시각을 함께 확인할 수 있습니다. 타임라인의 이벤트 이름이나 막대를 누르면 상세 화면에서 편집·삭제할 수 있습니다.

시작·종료는 UTC로 저장하고 브랜딩의 `timezone`(기본 `UTC`)으로 입력·표시합니다. 예를 들어 `Asia/Seoul`에서 09:00을 입력하면 00:00 UTC로 저장됩니다. 날짜 구간은 `[시작, 종료)`입니다. 설정한 시간대에서 9월 10일 00:00에 끝난 이벤트는 9월 9일까지 표시됩니다. 종료 시각 미정은 시작 이후 모든 날짜에 이어집니다. 미래 일정도 수기로 기록할 수 있습니다.

이벤트 추가·편집에서는 날짜를 달력으로 선택하고 시(`00`~`23`)와 분(`00`~`59`)을 각각 선택합니다. 브라우저 지역 설정과 관계없이 24시간제를 사용합니다. 하루의 끝은 다음 날짜의 `00:00`으로 입력합니다. 종료 시각 미정을 선택하면 종료 날짜와 시간 선택이 함께 비활성화됩니다.

서머타임 전환일의 타임라인은 해당 날짜의 실제 경과 시간으로 막대와 현재 시각을 배치합니다. 전환으로 존재하지 않거나 두 번 나타나는 시각은 새 입력으로 저장하지 않고 안내합니다. 기존 이벤트의 시각을 변경하지 않고 제목·내용만 편집하면 원래 UTC 시각과 초·밀리초를 유지합니다.

1차 버전에는 알림 발송과 이벤트 조회 배치를 포함하지 않습니다. 2차는 알림 발송, 3차는 커넥터 기반 이벤트 조회 배치입니다. 화면 및 단계별 요구사항은 [기획 명세](docs/specification.md)에 기록했습니다.

## 암호화와 로그인

1. 최초 접근 시 12~256자 비밀번호를 설정합니다. 확인 입력은 화면에서 검사합니다.
2. 무작위 salt와 scrypt (`N=131072`, `r=8`, `p=1`)로 256비트 암호화 키를 도출합니다.
3. 이벤트, 상세 내용, 생성·수정 시각을 포함한 상태 전체를 AES-256-GCM으로 암호화합니다.
4. 파일에는 버전·KDF 설정·salt·nonce·인증 태그·암호문만 저장합니다. 비밀번호, 암호화 키, 평문 이벤트는 저장하지 않습니다.
5. 로그인마다 암호문의 인증 태그와 복호화된 형식을 확인합니다. 잘못된 비밀번호나 변조된 데이터로는 로그인할 수 없습니다.
6. 서버 메모리에 복호화 키와 데이터를 유지합니다. 별도 브라우저는 서버가 열려 있어도 각각 로그인해야 합니다.
7. 로그아웃은 해당 브라우저 세션만 만료시킵니다. 서버 재시작 시 키와 모든 세션이 사라집니다.

쿠키는 `HttpOnly`, `SameSite=Strict`이며 HTTPS에서 `Secure`를 사용합니다. 로그인 요청 수를 제한하고, 쓰기 요청의 Origin을 검사합니다. 비밀번호·이벤트 내용을 요청 로그에 출력하지 않으며 브라우저의 localStorage/IndexedDB에도 저장하지 않습니다.

배포용 SSH 키와 앱 암호화 비밀번호는 다른 것입니다. **앱 비밀번호는 GitHub Actions Secrets, `.env`, workflow에 넣지 않습니다.** 배포로 앱을 재시작한 뒤에는 사람이 화면에서 다시 로그인해야 합니다.

이 설계는 저장 파일 보호를 위한 것입니다. 실행 중 서버는 키와 평문을 취급합니다. 메모리 덤프·스왑·호스트 전체 백업에 메모리가 포함되는지는 OS 운영 설정에 따릅니다. 모두 같은 비밀번호를 사용하는 동일 권한 모델이며 사용자별 권한·작성자 식별은 제공하지 않습니다.

## 저장·백업·복구

```text
data/
  store.json       # 현재 암호문
  store.json.bak   # 직전 저장 시점의 암호문
  .process-lock    # 중복 실행 방지용 PID와 임의 토큰, 암호화 키 아님
```

- 단일 앱 프로세스가 데이터를 메모리에 읽고, 변경마다 전체 상태를 암호화해 저장합니다.
- 쓰기는 큐로 순서를 보장합니다. 임시 파일 쓰기·동기화 완료 후 기존 파일을 교체합니다. 직전 암호화 파일은 `.bak`에 남깁니다.
- 같은 저장 디렉터리를 두 서버가 동시에 열면 시작을 거부합니다. 로컬 디스크에서 운영하며 네트워크 공유 파일시스템·여러 호스트의 공유 저장은 지원하지 않습니다.
- 이벤트별 버전을 검사하여 다른 화면의 오래된 편집·삭제가 최신 기록을 덮어쓰지 않게 합니다.
- 최대 20,000개 이벤트, 암호화 파일 최대 64MB를 지원합니다. 자동으로 이벤트를 삭제하지 않습니다. 장기간 대량 수집은 3차 구현 전에 별도 보관 정책을 정해야 합니다.
- `.bak`은 직전 버전 하나이며 장기 백업이 아닙니다. 운영자는 암호화된 데이터 파일을 별도 경로에 주기적으로 백업해야 합니다.
- 디스크 부족 등으로 저장이 실패하면 오류를 알립니다. 파일 교체 방식은 일반적인 중간 쓰기 손상을 줄이지만 저장 장치·파일시스템의 모든 장애를 복구하지는 못합니다.

복구 시에는 서버를 종료한 뒤 현재 데이터 디렉터리를 다른 이름으로 **보존**하고, 검증된 백업 `store.json`을 새 데이터 디렉터리에 넣어 다시 실행합니다. 백업을 암호화한 비밀번호가 필요합니다. 읽기 실패나 로그인 실패가 자동 초기화를 유발하지 않습니다.

비밀번호를 분실했다면 기존 데이터를 복호화할 수 없습니다. 초기화는 운영자가 서버를 종료하고 기존 데이터 디렉터리를 보존한 후 **비어 있는 새 `DATA_DIR`**로 실행하는 방식으로 수행합니다. 웹에는 익명 초기화·삭제 API가 없습니다.

비정상 종료 뒤 `.process-lock`이 남으면 서버가 PID의 존재를 확인합니다. PID가 사용 중이거나 잠금 파일이 손상된 경우 다른 프로세스가 이 데이터를 사용하지 않는지 운영자가 확인한 후 잠금 파일을 제거해야 합니다.

## 서버 배포

[배포 문서](docs/deployment.md), [수동 실행 workflow](.github/workflows/deploy.yml), [systemd 서비스 예시](deploy/service-timeline.service.example)를 제공합니다. 실제 IP·사용자·경로·키는 포함하지 않았습니다.

workflow는 기본적으로 비활성화되어 있으며 배포할 저장소의 `DEPLOY_ENABLED=true` 및 접속 설정이 있어야 실행됩니다. Linux self-hosted runner에서 Git·Bash·tar·OpenSSH를 사용합니다. 외부 Action 다운로드, 패키지 설치, 빌드 단계는 없습니다.

## 검증

```sh
node --test test/date-utils.test.mjs test/server.test.mjs
```

암호화·잘못된 키·파일 변조·손상 보존, 세션 격리, 동시 쓰기·수정 충돌, 재시작 복원, 날짜 경계·주간 레인을 검증합니다. 실제 운영 디렉터리를 사용하지 않습니다.

이미 설치된 Chromium 계열 브라우저로 화면을 검증할 수도 있습니다.

```sh
node scripts/browser-check.mjs
```

Windows의 기본 Microsoft Edge 경로를 사용합니다. 다른 환경에서는 `BROWSER_PATH` 환경 변수에 Chrome/Chromium/Edge 실행 파일 경로를 지정하세요. 브라우저를 추가로 다운로드하지 않습니다. 테스트용 서버·프로필·암호화 파일을 임시 생성한 뒤 정리하며, 캡처는 `.tmp/screenshots/`에 남깁니다.
