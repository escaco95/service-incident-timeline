# 워크플로우 사용 안내

이벤트와 서비스는 일정·표시 정보를 관리하고 호출·분기·성공 판정은 워크플로우에서 정의한다. 정의와 실행 기록은 암호화 저장한다.

JSON 파일 규격, 노드 설정과 서비스별 실행·보류 규칙은 [JSON 작성 및 연동 안내](workflow-authoring.md)에 정의한다.

## 구성하고 실행하기

1. 워크플로우 목록에서 **새 워크플로우**를 생성한다. 초기 상태는 OFF다.
2. 이름을 편집하고 이벤트 시작·이벤트 종료·크론·서비스 상태 변경 중 트리거 하나를 배치한다. 컨텍스트 값 주입, 조건, switch 분기, 목록 검색, 날짜·시각, API 호출, 워크플로우 종료 노드를 추가하고 출력 연결점을 눌러 다음 노드와 연결한다.
3. **저장**으로 적용한다. OFF인 초안은 설정이 미완성이어도 저장할 수 있다. 순환 연결이나 잘못된 연결은 초안에서도 저장하지 않는다. ON 또는 수동 실행 시에는 모든 노드가 트리거에서 연결되고 설정이 유효해야 한다.
4. **수동 실행**으로 저장된 구성을 실행한다. 이벤트 시작·종료 트리거라면 입력 이벤트를 선택하고, 서비스 상태 변경 트리거라면 서비스 문자열을 입력해 현재 상태를 평가한다. 자동 실행이 OFF여도 수동 실행은 가능하다.
5. 목록에서 **ON**으로 전환하면 이후 발생하는 트리거를 자동 실행한다. ON 상태에서 저장한 수정은 이후 접수되는 실행에 적용한다. 실행 중인 기록은 접수 당시 구성으로 계속 실행한다. OFF는 이후 자동 접수를 막으며 이미 접수한 실행은 이력에서 별도로 중지한다.
6. **실행 이력**에서 결과·입력·노드별 결과를 확인한다. 종료된 일반 실행은 **같은 버전·입력으로 다시 실행**하고, 서비스 실행은 **현재 서비스 상태 재평가**를 사용한다.

저장하지 않은 변경은 실행에 반영되지 않는다. **저장된 내용으로 되돌리기**는 마지막으로 저장한 구성으로 되돌린다. **다시 불러오기**는 서버의 최신 구성을 가져온다. 다른 화면에서 저장·ON/OFF를 변경했다면 버전 충돌을 표시한다. 메뉴를 이동해도 편집 초안은 유지되며 새로고침 전에는 저장하지 않은 변경을 알린다. 삭제 시 확인 팝업을 표시하고 대기·실행 중 작업을 중지한다. 실행 이력은 로그 보관 정책에 따라 남는다.

## 편집 화면

다이어그램은 공통 내비게이션 아래 본문 전체를 사용한다. 상단 작업 도구, 왼쪽 노드 목록, 오른쪽 노드 설정, 하단 확대·축소 도구는 캔버스 위에 떠 있는 패널이다. 상단의 **노드 목록 / 노드 설정** 버튼이나 각 패널의 닫기 버튼으로 접고 펼친다. 목록과 설정은 패널 안에서 스크롤하며, **화면에 맞추기**는 열려 있는 패널을 피해 노드를 배치한다. 좁은 화면에서는 패널을 한 번에 하나씩 열며 노드 설정은 하단에 표시한다. 패널 표시와 화면 이동·확대 상태는 워크플로우 정의를 변경하지 않는다.

노드를 이동·추가·복제하거나 자동 정렬하면 18px 격자의 `(0, 0)`~`(5004, 5004)` 영역에 배치한다. 노드와 연결점·라벨은 경계 안에 머물며 긴 흐름은 여러 열로 정렬한다. 배경을 **우클릭 드래그**해 화면을 이동하고 마우스 휠로 확대·축소한다. 터치 화면에서는 배경을 한 손가락으로 끌어 이동한다.

**자동 정렬**은 연결 관계에 따라 단계를 나누고, 같은 단계의 분기를 출력 순서에 맞춰 나란히 배치한다. 합류점은 선행 경로 뒤에 놓으며, 높이가 부족하면 단계 간격을 줄인다. 그래도 부족한 흐름은 단계 묶음을 오른쪽 열로 이어 배치한다. 한 단계가 열 너비를 넘으면 출력 순서를 유지하며 여러 행으로 나눈다. 각 열은 위에서 아래로 읽고, 열 사이의 연결은 화살표 방향으로 따라간다. 재정렬해도 결과는 같으며 노드 위치만 변경한다.

연결선은 노드와 출력 라벨을 피해 꺾어서 표시한다. 연결을 선택하거나 가리키면 해당 경로가 강조된다. 여러 경로가 같은 합류점으로 향하면 일부 구간을 공유하거나 서로 교차할 수 있다. 수동으로 노드를 겹쳐 놓아 회피 경로를 만들 수 없으면 기본 곡선으로 표시한다. **화면에 맞추기**는 큰 그래프도 전체를 볼 수 있도록 최소 5%까지 축소하며, 세부 내용은 원하는 위치에서 확대해 확인한다.

배경을 **좌클릭 드래그**하면 선택 사각형에 닿는 노드를 함께 선택한다. 영역을 선택하는 동안과 여러 노드가 선택된 상태에서는 노드 속성을 편집할 수 없다. 선택을 마친 뒤 설정 패널의 **복제·삭제** 또는 **Delete**로 일괄 작업할 수 있다. 선택된 노드를 좌클릭으로 끌면 노드 사이의 간격과 연결을 유지한 채 함께 이동하며, 선택 전체의 외곽을 하나로 계산해 경계 안에 둔다. 빈 배경 클릭이나 **Esc**로 선택을 해제하며, 드래그 중 Esc는 해당 드래그를 취소한다.

여러 노드를 복제하면 선택된 노드 사이의 연결도 복제하고, 복제된 노드를 가리키는 값 경로와 템플릿을 새 ID로 바꾼다. 선택 밖 노드와의 연결은 복제하지 않는다. 컨텍스트 주입 값·switch 분기 값 같은 고정 문자열은 그대로 유지한다. 전체 노드·연결 제한을 넘으면 일부만 복제하지 않고 작업 전체를 거부한다.

실행을 막는 오류가 있으면 하단에 **오류 진단** 패널을 표시하고 관련 노드에 적색 외곽선을 표시한다. 시작 이벤트가 여러 개면 해당 이벤트 노드를 모두 표시하며, 목록에서는 각 노드를 개별 항목으로 선택할 수 있다. 항목 클릭은 캔버스의 노드 클릭과 동일하게 선택·설정을 열고, 더블 클릭 또는 **Alt+Enter**는 해당 노드를 열린 패널을 제외한 캔버스 중앙으로 이동한다. 오류 건수는 같은 원인에 관련된 여러 노드를 한 건으로 센다.

노드 설정과 연결을 수정하면 진단을 자동 갱신하며, 해결된 오류의 외곽선과 목록 항목은 사라진다. 패널을 접어도 적색 외곽선은 유지한다. OFF 초안은 실행 오류가 있어도 기존 저장 조건에 따라 저장할 수 있지만 수동 실행은 오류를 해결하고 저장한 뒤 가능하다. ON 상태의 저장 검증과 순환·잘못된 연결의 저장 제한은 유지된다. 진단은 현재 편집 내용을 검사하며 실제 API 호출이나 실행 이력을 생성하지 않는다.

## Dry-Run 테스트

편집 화면 상단의 **Dry-Run 테스트**를 누르면 현재 편집 중인 노드에 맞춘 설정 팝업이 열린다. 저장 전 수정도 테스트할 수 있다. 실제 API를 호출하지 않으며 **테스트 실행과 입력값 저장 모두 감사 로그·실제 실행 이력을 생성하지 않는다.** 자동 실행 상태·서비스 상태·보류도 변경하지 않는다.

- 이벤트 시작·종료: 이벤트 JSON 초기값과 트리거 JSON 초기값을 직접 입력하거나 **등록 일정에서 시작/종료 상황 불러오기**를 펼쳐 일정을 선택한다. 목록은 이전·다음 페이지로 탐색할 수 있다. 적용할 때 최신 일정의 제목·설명·분류·서비스·시각을 불러오고, 노드 종류에 맞는 시작/종료 시각을 `trigger.scheduledAt`과 테스트 기준 시각에 채운다. 종료 미정 일정은 종료 노드에서 선택할 수 없다. 적용 후 JSON을 직접 수정할 수 있고, 입력값은 당시 스냅샷으로 보존되므로 이후 일정 변경이 다음 테스트값을 바꾸지 않는다. 최신 정보를 다시 쓰려면 일정을 재적용한다. 일정 조회·적용도 감사 로그를 생성하지 않는다.
- 크론: 예정 시각·시간대 등의 트리거 초기값을 입력한다. 예약 대기 없이 트리거 이후의 흐름을 테스트한다.
- 서비스 상태 변경: 트리거 JSON을 직접 입력하거나 **등록 일정으로 서비스 상태 변경 재현**을 펼친다. 일정·시작/종료·서비스를 고르면 해당 시각 직전과 직후의 모든 중첩 일정을 실제 실행기와 같은 방식으로 집계한다. 여러 서비스가 있으면 하나를 선택하고, 노드의 대상 서비스 설정이 있으면 그 문자열에 맞춘다. 시작 포함·종료 제외, 동시에 시작/종료되는 일정, 종료 미정, 장애 우선순위를 반영해 `previous`, `severity`, `events`와 테스트 시각을 채운다. 선택한 일정이 종료되어도 다른 일정이 남아 있으면 그 상태가 유지된다. 상태가 같으면 실제 자동 실행이 발생하지 않으므로 일정 재현 Dry-Run도 후속 단계를 생략한다. 트리거 JSON을 직접 수정하면 일정 재현 모드를 해제하고 직접 입력한 값으로 후속 흐름을 테스트한다.
- API 호출: 노드별 HTTP 상태 코드·응답 헤더·JSON 본문 또는 통신 오류 메시지를 지정한다. 템플릿 치환 후 요청 미리보기를 보여주며 실제 요청은 보내지 않는다.
- 날짜·시각: 팝업의 테스트 기준 시각을 `now`로 사용한다. 컨텍스트 주입·조건·switch 분기·목록 검색·종료는 노드 설정과 앞선 테스트 결과를 사용한다.

**Dry-Run 실행** 후 팝업에서 실행 순서, 선택한 분기, 노드별 출력·오류, 실행하지 않은 노드와 최종 컨텍스트를 확인한다. HTTP 4xx·5xx는 실제 실행과 동일하게 작성한 조건으로 판정한다. 조회 요청의 통신 오류는 stop/continue/branch를 따르고, 변경 요청의 통신 오류는 확인 필요로 끝나지만 서비스 보류를 만들지 않는다.

입력값은 워크플로우·노드 ID별로 자동 저장하며 닫기·Esc에서도 마지막 입력을 저장한다. 작성 중인 불완전한 JSON도 입력값으로 보존하고 실행 시 검증한다. 팝업 재열기·새로고침·서버 재시작 후 복원된다. 테스트값은 암호화 저장하고 실제 정의 버전·자동 실행에는 영향을 주지 않는다. 일반 워크플로우 JSON 다운로드에는 포함하지 않으며 전체 백업·복원에는 포함된다. 다른 화면의 입력값과 충돌하면 덮어쓰지 않고 서버 설정을 다시 불러올 수 있다.

서비스 상태 재현은 **현재 등록된 일정**을 선택한 시각에 대입한 결과이며, 삭제·수정 전의 과거 일정이나 실제 실행 이력을 복원하지 않는다. `generation`은 현재 저장된 서비스 세대에 이번 모의 상태 변경을 반영한다(변경 시 +1, 미변경 시 유지). 실제 서비스 세대·보류·상태·감사 로그는 변경하지 않는다. 재현 출처와 계산된 초기값도 함께 보존하며, 최신 일정을 반영하려면 재적용한다.

## 트리거 기준

서비스 상태 변경 트리거는 현재 활성 이벤트를 서비스 문자열별로 집계하고 심각도가 달라질 때 실행한다. 최초 평가에서는 기준점만 저장한다. 집계 입력과 재시작·보류 처리 기준은 [서비스 상태 변경 트리거](workflow-authoring.md#서비스-상태-변경-트리거)를 따른다. 이벤트 시작·종료와 크론의 기준은 다음과 같다.

- 이벤트 시작·종료는 이벤트에 입력한 시작·종료 시각을 기준으로 한다. 생성·수정 동작 자체는 트리거가 아니다. 종료 미정 이벤트에는 종료 트리거가 없다.
- **이미 지난 시각은 소급 실행하지 않는다.** 늦게 등록하거나 지난 시각으로 수정한 일정, OFF 구간, 서버 재시작 전의 누락 일정은 자동 보충하지 않는다.
- 서비스를 비워 두거나 ‘모든 서비스’로 설정하면 모든 이벤트를 대상으로 한다. 서비스 ID 또는 이벤트 선택 당시 표시명을 입력하면 해당 서비스를 포함한 이벤트만 실행한다.
- 같은 워크플로우·트리거 노드·이벤트·예정 시각은 중복 접수하지 않는다. 이벤트 시각을 미래로 옮기면 새로운 예정 시각으로 실행할 수 있다.
- cron 형식은 **분 시 일 월 요일**이다. 숫자, 별표, 범위, 목록, 간격을 지원한다. 예: `0 9 * * 1-5`는 선택한 시간대의 평일 오전 9시다. 요일은 일요일 0 또는 7, 월요일 1이다. 일과 요일을 모두 지정하면 둘 중 하나가 일치해도 실행한다.
- 시간대는 서버에서 IANA 이름으로 검증한다. 화면은 Asia/Seoul·UTC·Asia/Tokyo를 제공한다. 서머타임으로 같은 현지 분이 반복되면 한 번만 실행하고 존재하지 않는 분은 건너뛴다.
- 서버는 약 1초 간격으로 확인한다. 짧은 처리 지연은 다음 확인에서 접수하고, 1분을 넘는 중단 구간은 역산하여 채우지 않는다.
- 서버 재시작 후 첫 로그인으로 암호화 저장소를 열어야 자동 실행을 시작한다. 이후 브라우저 종료·로그아웃은 서버의 자동 실행을 중지하지 않는다.

## 조건·HTTP·종료

조건은 값의 경로와 같음·다름·포함·값 존재·숫자 비교를 지원한다. 숫자와 true/false는 해당 JSON 자료형으로 비교한다. 일반 문자열은 그대로 입력하며 숫자처럼 생긴 문자열을 비교하려면 JSON 문자열로 입력한다. 조건 결과에 따라 일치 또는 불일치 연결 하나를 실행한다. 연결이 없는 출력에 도달하면 해당 경로는 성공으로 끝난다.

HTTP는 GET·POST·PUT·PATCH·DELETE·HEAD, URL, JSON 헤더, 요청 본문을 설정한다. GET·HEAD는 본문을 보내지 않는다. HTTP 4xx·5xx 응답도 상태·헤더·본문을 출력한다. **이 응답 때문에 전체 워크플로우를 실패시킬지는 작성자가 조건과 종료 노드로 결정한다.** 예를 들어 response.status가 400 이상이면 실패 종료로 연결하거나 response.body.accepted가 true면 성공 종료로 연결한다.

조회 요청의 통신 오류와 timeout·응답 크기 초과에는 다음 중 하나를 선택한다.

- 워크플로우 실패로 종료
- 다음 노드로 계속 진행: response.error에 오류가 있고 status·body는 null
- 오류 연결로 진행: 정상 출력과 별도로 오류 연결을 필수 지정

조회 요청의 통신 오류 재시도는 기본 0회, 최대 3회다. 변경 요청 재시도는 검증된 외부 중복 방지를 명시해야 하며, 응답 유실은 확인 필요로 처리한다. 같은 요청을 반복하며 HTTP 4xx·5xx를 자동 재시도하지 않는다. 제한 시간은 요청당 100~30,000ms, 전체 실행은 120초다. 응답 본문은 최대 128KiB이며 이력에는 기록 정책을 적용하고 가린 출력의 최대 16,000자를 기록한다. 이후 노드의 조건·변수는 잘리지 않은 응답을 사용한다. 리다이렉트는 자동으로 따라가지 않는다. http/https만 지원하고 URL 안의 인증 정보·fragment 및 알려진 클라우드 메타데이터 주소는 허용하지 않는다. 사내 HTTP 주소는 서버가 접속 가능한 범위에서 사용할 수 있다.

종료 노드에서 성공(`success`)·실패(`failure`)·확인 필요(`review`)·생략(`skipped`)과 사유를 지정한다. 각 출력은 다음 노드 하나로 연결한다. 병렬 분기와 순환 루프는 제공하지 않는다. switch 분기·목록 검색·날짜 변환과 JSON 자료형을 보존하는 값 삽입은 [노드 설정](workflow-authoring.md#조건분기검색시각json-값)을 참고한다.

## 변수와 비밀 값

URL·헤더 값·본문·종료 사유에서 이중 중괄호 경로를 사용한다.

| 경로 예시 | 값 |
| --- | --- |
| {{event.id}}, {{event.title}}, {{event.category}} | 접수 당시 이벤트 |
| {{event.services.0.id}}, {{event.services.0.label}} | 이벤트의 서비스 선택 |
| {{trigger.type}}, {{trigger.scheduledAt}} | 트리거 종류와 예정 시각 |
| {{response.status}}, {{response.body.id}} | 가장 최근 HTTP 응답 |
| {{nodes.노드ID.body.id}} | 앞서 실행한 특정 노드의 출력 |
| {{run.id}} | 이번 실행 식별자 |
| {{context.token}} | 앞서 실행한 컨텍스트 값 주입 노드에서 지정한 문자열 |
| {{secrets.token}} | 기존에 등록된 비밀 변수 (삭제만 가능) |

URL에 삽입하는 값은 URI 구성 요소로 인코딩한다. 완전한 URL 자체를 변수로 대체하는 대신 URL의 경로·쿼리에 변수를 넣는다. JSON 본문에 있는 문자열 변수는 따옴표와 줄바꿈을 보존하며 JSON 형식을 유지한다. 없는 변수와 지원하지 않는 경로는 오류다. JavaScript 코드를 실행하지 않는다. cron 입력의 event는 null이다.

**컨텍스트 값 주입** 노드를 더블 클릭하면 키·값 목록을 편집하는 팝업이 열린다. 키·값을 추가·삭제하고 **적용**한 뒤 워크플로우를 **저장**한다. 키보드 Enter 또는 노드 설정의 **키·값 편집** 버튼으로도 열 수 있다. 취소·Esc는 팝업에서 편집한 내용을 버린다.

노드가 실행되면 키·값이 이번 실행의 `context`에 추가된다. 이후 노드에서 `{{context.token}}`처럼 참조한다. 같은 키를 다시 주입하면 이후에는 새 값이 적용되고 다른 키는 유지된다. 값은 문자열 그대로 저장하며 그 안의 `{{...}}`는 다시 치환하지 않는다. 트리거 직후 또는 흐름 중간에 배치할 수 있고, 참조하는 모든 경로에서 먼저 주입되어야 한다. 실행마다 컨텍스트는 새로 시작하며 재실행에는 당시 정의의 주입 값을 사용한다.

기존 **비밀 변수** 영역은 등록된 변수가 있을 때만 표시하며 이름과 삭제 버튼만 제공한다. 삭제는 워크플로우 저장 시 반영하고, 저장 전에는 **저장된 내용으로 되돌리기**로 취소할 수 있다. UI와 API 모두 신규 등록·값 변경을 허용하지 않는다. 기존 값과 `{{secrets.token}}` 참조는 유지된다. ON 상태에서 참조 중인 비밀 변수를 삭제하려면 참조를 컨텍스트 값으로 바꾸거나 먼저 OFF로 전환한다.

정의와 실행 입력은 암호화 저장한다. 컨텍스트 주입 값은 편집·조회 API와 JSON 다운로드에 포함된다. 실행 상세에서는 주입 설정의 값과 HTTP URL·헤더·본문 원문을 가린다. 인증·비밀 값에 해당하는 키(token, password 등)의 주입 값은 실행 출력에서도 가린다. 기존 비밀 변수 값은 편집·조회 API와 워크플로우 JSON 다운로드에 포함되지 않는다.

## 실행 이력과 중단

실행마다 정의 버전·입력·트리거·상태·시작/종료 시각·노드별 출력·HTTP 시도를 남긴다. 실행 당시 그래프에서 실제로 거친 노드와 연결을 표시한다. 대기 또는 실행 중 작업은 중지할 수 있지만 이미 대상 API에 도착한 요청의 효과를 되돌리지는 않는다.

일반 실행의 다시 실행은 당시 정의와 입력을 복제한 **새 실행**이다. 비밀 변수는 현재 저장된 값을 사용한다. 원래 실행 ID를 연결해 추적하며, 기존 실행의 성공한 호출도 처음부터 반복될 수 있음을 확인한 뒤 실행한다. 서비스 실행은 최신 정의·현재 입력을 사용하는 **현재 서비스 상태 재평가**로 새 실행을 만든다. 삭제된 워크플로우는 다시 실행할 수 없다.

요청 시도는 API를 호출하기 전에 저장하고 결과를 저장한 뒤 다음 노드로 이동한다. 기록 저장 실패 시 후속 호출과 새로운 실행을 멈춘다. 서버 종료·비정상 재시작 당시 끝나지 않은 작업은 중단으로 기록한다. 외부 호출의 적용 여부를 알 수 없으므로 자동 재개하지 않는다.

단일 서버 프로세스에서 전체 최대 2개 실행, 같은 워크플로우는 한 번에 1개를 실행한다. 워크플로우 최대 100개, 구성당 노드 100개·연결 200개, 하루 실행 이력 10,000건을 지원한다. 보관 기간과 날짜별 파일 정리는 시스템의 로그 관리 정책을 따른다.

## 인증 API

모든 경로는 로그인 세션을 요구한다. 쓰기는 동일 출처 JSON 요청이다. 생성·수동 실행·재실행의 requestId는 클라이언트가 생성한 8~100자 식별자이며 같은 요청을 재전송할 때 같은 값을 유지한다.

| API | 역할 |
| --- | --- |
| GET /api/workflows | 목록·마지막 실행 정보·실행기 상태 |
| POST /api/workflows | OFF 초안 생성: name, nodes, edges, requestId |
| GET /api/workflows/:id | 저장된 정의·버전·비밀 변수 이름 |
| PUT /api/workflows/:id | name, nodes, edges, version 저장 및 선택적 secrets의 기존 항목 삭제(null) |
| GET /api/workflows/:id/dry-run-setup | 저장된 Dry-Run 입력값과 별도 버전 |
| PUT /api/workflows/:id/dry-run-setup | Dry-Run 입력값 저장 (감사 로그 없음) |
| POST /api/workflows/:id/dry-run | 전달한 편집 정의와 테스트값으로 모의 실행 (감사 로그·실행 이력 없음) |
| POST /api/workflows/:id/dry-run-service-event | eventId·occurrence(start/end)·service로 일정 경계 전후의 서비스 트리거 계산 (읽기 전용, 감사 로그 없음) |
| PUT /api/workflows/:id/enabled | version, enabled로 ON/OFF |
| DELETE /api/workflows/:id | version을 확인해 삭제 |
| POST /api/workflows/:id/run | version, requestId와 트리거에 따른 eventId 또는 service로 접수 |
| GET /api/workflow-runs/:id | 가린 입력·구성·노드별 결과 |
| POST /api/workflow-runs/:id/cancel | 대기·실행 중 작업 중지 |
| POST /api/workflow-runs/:id/rerun | requestId로 일반 실행의 당시 구성·입력을 다시 접수 |
| GET /api/audit?kind=workflows | 기간·워크플로우·이벤트·서비스·결과별 실행 이력 |

파일 검증·다운로드와 서비스 상태 조회·보류 해소·재평가 API는 [작성 안내의 API](workflow-authoring.md#api)에 정의한다. 구현 파일과 검증 명령은 [개발 안내](development.md)를 참고한다.
