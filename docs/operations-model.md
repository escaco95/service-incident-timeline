# 서비스 모델과 상태 계산

이 문서는 [이슈 #1](https://github.com/escaco95/service-incident-timeline/issues/1)의 첫 구현 단계를 설명한다. 서비스 다중 선택·업무 설정·상태 계산·미리보기와 커넥터 계약 초안을 제공한다. 웹에서 실제 외부 API를 호출하는 실행기와 예약·재시도·outbox·실행 이력 화면은 아직 제공하지 않는다.

## 화면에서 사용하기

1. 로그인 후 상단 **설정 → 서비스 제안 목록·상태 정책**을 연다.
2. 서비스의 고정 ID·표시명·활성 여부·커넥터 ID를 등록한다. 위·아래 버튼으로 표시 순서를 바꾼다. 기존 ID는 수정·삭제하지 않고 비활성화한다.
3. 범용 상태 ID·표시명·우선순위와 기준 상태를 등록한다. 우선순위가 클수록 우선한다. 동순위는 상태 목록 순서 또는 나중에 시작한 이벤트로 결정한다.
4. 이벤트 편집에서 제안 서비스를 검색·선택하거나 서비스명을 직접 추가한다. 직접 입력 항목의 연결 대상은 별도로 선택한다. 같은 이름의 다른 서비스 ID는 서로 다른 대상으로 유지한다.
5. **상태 계산 설정**에서 포함 여부·상태 영향·종료 방식을 지정한다. 처음 포함하거나 적용 범위가 바뀌면 확인 체크를 선택한다. 미연결·비활성 대상이나 정책에 없는 상태 영향은 포함할 수 없다.
6. **설정 → 대상별 상태 미리보기**에서 평가 날짜·24시간제 시각과 기간을 선택한다. 유형 필터와 무관하게 대상별 상태·근거 이벤트·예상 변경·제외 사유를 조회한다.

기준 상태는 외부 서비스가 정상이라는 보장이 아니다. 미리보기는 실제 상태를 조회하지 않으며 `externalCalls: false`, `externalState: null`로 반환한다. 현재의 포함 체크는 계산 범위를 설정하는 단계이고 실제 API 실행을 시작하지 않는다.

## 저장과 이관

기존 AES-256-GCM JSON 봉투 형식과 비밀번호·원자적 파일 교체·백업 방식을 유지한다. 복호화한 내부 데이터의 `schemaVersion`을 2로 올린다.

```json
{
  "schemaVersion": 2,
  "revision": 1,
  "events": [],
  "operations": {
    "version": 1,
    "services": [],
    "policy": { "version": 1, "baseline": null, "tieBreak": "state-order", "states": [] }
  },
  "changes": []
}
```

날짜 등 기존 저장 필드는 계속 보존한다. 서비스·정책 목록의 초기값은 빈 목록이며 공개 코어에 사내 서비스나 특정 상태 정책을 고정하지 않는다. [가상 설정 예제](../examples/operations.example.json)를 참고해 UI 또는 인증된 설정 API로 배포별 설정을 공급할 수 있다. 실제 서비스 목록을 공개 저장소의 예제 파일에 넣지 않는다.

schema 1을 열 때 기존 `service` 문자열은 `{ kind: "custom", label: 기존 값, targetId: null }` 하나로, 빈 값은 빈 목록으로 이관한다. 이벤트 ID·버전·제목·시각·설명을 보존하고 모두 계산 비활성으로 둔다. 로그인·조회만으로 원본 파일을 덮어쓰지 않는다. 다음 업무 쓰기 때 schema 2로 저장하고 `.bak`에 쓰기 직전 파일을 보존한다.

배포 전 데이터 파일의 별도 백업을 보관한다. schema 2를 저장한 뒤 이전 바이너리로 되돌리려면 서버를 종료하고 당시 schema 1 백업을 별도의 데이터 디렉터리로 복구해야 한다. 현재 파일을 삭제하거나 자동 초기화하지 않는다.

## 서비스와 적용 범위

제안 항목은 `id`, `name`, `active`, `order`, `connectorId`, `mappingVersion`을 갖는다. `connectorId`는 담당자가 확정한 서버 모듈 연결의 논리 ID다. 이 단계는 모듈이 실제 배포되었는지 확인하는 실행 준비 검사까지 수행하지 않는다.

이벤트의 `services`는 다음 두 형태를 구분한다.

```json
[
  { "kind": "catalog", "id": "resource-a", "label": "가상 서비스 A" },
  { "kind": "custom", "label": "직접 입력 기록", "targetId": "resource-b" }
]
```

선택 당시 표시명을 저장해 이후 제안 목록 이름을 바꾸더라도 과거 기록을 바꾸지 않는다. 직접 입력은 자동으로 전역 목록이나 연결을 만들지 않는다. 모든 대상을 선택하더라도 그때의 명시적인 ID 배열만 저장하며 새 서비스를 추가해도 기존 이벤트 범위가 늘어나지 않는다. `service` 응답 필드는 기존 화면·클라이언트용 표시 문자열로 유지하지만 상태 계산에는 사용하지 않는다. 복수·연결 서비스가 있는 이벤트는 구형 단일 서비스 API로 대상을 변경할 수 없다.

`execution`은 `enabled`, `impact`, `endMode`, `confirmedEnd`, `authorization`을 가진다. `authorization`은 비밀번호·인증 토큰이 아니라 사용자가 확인한 범위의 서버 생성 지문이다. 서비스 ID·커넥터 ID·연결 버전·일정·영향·종료 방식·확인 종료 시각·정책 버전을 묶는다. 클라이언트가 보낸 임의 지문은 신뢰하지 않는다.

범위를 확인하는 요청에는 `confirmAuthorization: true`와 화면에서 읽은 업무 설정의 `confirmSettingsVersion`을 함께 보낸다. 실제 저장 시점의 설정 버전이 다르면 409로 거부한다. 확인 중에 바뀐 연결·정책으로 자동 승인하지 않으며, 편집 창을 다시 열어 최신 범위를 확인해야 한다. 이 두 필드는 요청에만 사용하고 저장하지 않는다.

대상 연결이나 활성 여부를 바꾸면 연결 버전이 증가한다. 비활성 후 다시 활성화해도 기존 범위를 자동으로 승인하지 않는다. 표시명·표시 순서 변경은 연결 버전을 바꾸지 않는다. 정책 내용이 바뀌면 정책 버전이 증가한다. 이전 지문과 다르면 계산에서 보류하고 설정 화면의 영향을 받는 이벤트 목록에 표시한다. 이벤트의 적용 범위를 다시 확인해야 포함된다.

## 계산 규칙

- 포함 활성·정책·대상 연결·범위 확인을 통과한 이벤트만 계산한다.
- 시간 구간은 `[시작, 종료)`다. 종료 미정은 시작 이후 계속 활성이다.
- `scheduled` 방식은 `end`에서 종료한다. `confirmed` 방식은 예정 `end`를 지나도 유지하며 `confirmedEnd`에서 종료한다.
- 운영자 확인 종료는 이벤트 상세의 **종료 확인**으로 서버 현재 시각을 기록한다. 이벤트 버전 충돌을 검사한다. 정책·연결 변경으로 보류된 이벤트를 확인 종료했다고 새 정책에 자동 재승인하지 않는다.
- 캘린더의 일정 막대는 등록한 시작·예정 종료를 표시한다. 확인 종료 여부와 계산 영향은 상세·편집·미리보기에서 따로 확인한다.
- 각 대상에 대해 활성 이벤트 전체를 모아 우선순위로 결정한다. 상위 이벤트 종료 후 나머지 이벤트로 다시 계산한다.
- 동순위 정책 적용 후에도 같으면 상태 목록 순서와 이벤트 ID 순서로 결정한다. 기본 정렬은 실행 환경의 locale에 의존하지 않는다.
- 한 시각의 시작·종료를 한 번에 평가한다. 상태는 같고 근거만 바뀌면 예상 변경에 남기되 `applyRequired: false`로 반환한다.
- 과거의 전이를 따라 적용하지 않는다. 이 단계의 계획 조회는 읽기 전용이고 실제 재시작 처리·전송은 미래 실행기의 책임이다.

## 인증 API

기존 세션·동일 출처 검사를 사용한다. 서비스 목록은 `/api/branding`이나 로그인 전 HTML에 포함하지 않는다.

| 요청 | 동작 |
| --- | --- |
| `GET /api/operations/settings` | 서비스·정책·설정 버전과 재확인이 필요한 이벤트 조회 |
| `PUT /api/operations/settings` | `{version, services, policy}` 저장. 최신 설정 버전이 다르면 409 |
| `POST /api/operations/preview` | `{at?, until?}`. 생략 시 현재 상태, `until` 지정 시 예상 변경도 계산. UTC ISO 입력, 쓰기·호출 없음 |
| `GET /api/operations/changes?offset=0&limit=50` | 변경 이력 읽기. 최신순, 최대 200건 단위 |
| `POST /api/events/:id/confirm-end` | `{version}`으로 운영자 확인 종료 |
| 기존 이벤트 POST·PUT | `services`, `execution` 추가. 범위 확인은 `execution.confirmAuthorization: true`와 `execution.confirmSettingsVersion`으로 명시 |

서비스 목록 200개, 이벤트당 서비스 50개, 상태 정책 32개를 지원한다. 계획 조회는 366일·평가 경계 500개·예상 변경 5,000건·이벤트×평가 경계 2,000,000 이내로 제한한다. 한도를 넘으면 범위를 줄이라는 오류를 반환한다.

## 변경 이력과 다음 단계

이벤트 생성·수정·삭제·확인 종료와 서비스·정책 설정 변경은 같은 암호화된 저장 단위에서 변경 이력을 추가한다. 자유 서술 원문과 서비스 표시명을 복사하지 않고 대상·버전·시각·영향·설정 구조만 기록한다. 공유 비밀번호 모드의 행위자는 `shared-user`, 즉 사용자 조작·개인 식별 불가다. 쿠키나 세션 값을 기록하지 않는다.

이 단계의 변경 이력은 추가만 가능하며 50,000건과 기존 암호화 파일 64MB 한도를 넘으면 새 쓰기를 중단한다. 자동 삭제·보존 기간 설정·실행 이력 UI는 후속 작업이다. 임시 운용에서 한도에 도달하면 서버를 종료하고 전체 데이터 디렉터리를 보관한 뒤, 별도 `DATA_DIR`로 새 기록을 시작한다. 보관본은 같은 버전 서버와 기존 암호로 별도 열어 조회할 수 있다. 향후 미완료 작업·전이 ID·재시작 근거를 보존하는 정리 절차를 실행기와 함께 구현한다.

후속 범위는 [커넥터 계약 검토](connector-contract-v1.md), 영속 outbox·대상별 직렬화·예약 평가·재시도·지연 표시·실행 허용 제어·키 공급 모듈·실행 이력 화면이다. 현재 구현이나 데모를 이슈 #1 전체 완료 또는 무인 자동 실행으로 설명하지 않는다.
