# 비밀 값 저장소

**시스템 설정 → 비밀 값 저장소**에서 서버 공용 비밀 값을 등록·교체·삭제한다. 모든 워크플로우가 같은 키 공간을 사용한다. 로그인한 공유 계정은 같은 관리 권한을 가지며 워크플로우별 접근 제한은 제공하지 않는다.

## 저장과 관리

값은 앱의 기존 AES-256-GCM 암호화 저장소 안에 `secretStore: { version, entries }`로 보관한다. 별도 평문 설정 파일을 만들지 않는다. 저장소 잠금 해제 후 서버 메모리에서 값을 취급하며 호스트·실행 메모리의 보호 범위는 [암호화와 로그인](../README.md#암호화와-로그인)을 따른다. 기존 저장소에 이 필드가 없으면 빈 목록으로 취급하고 조회만으로 파일을 쓰지 않는다.

- 키는 영문 소문자로 시작하는 소문자·숫자·밑줄 1~64자다. `constructor`, `prototype`, `__proto__`는 사용할 수 없다. 점을 포함한 중첩 키와 별칭은 지원하지 않는다.
- 최대 50개, 값은 1~4,000자 문자열이다. 값의 앞뒤 공백과 템플릿처럼 보이는 문자열을 그대로 보존한다. 빈 값은 등록할 수 없다.
- 표의 열은 **키 / 새 비밀 값 / 관리**다. 각 행에는 키와 설정 여부를 표시하고 새 값을 입력해 해당 행에서 교체·삭제한다. 마지막 행에서 새 키를 등록한다. 기존 값을 다시 조회하거나 표시하는 기능은 없다. 제출한 입력값은 즉시 비우며 다른 행에서 작성 중인 입력은 유지한다. 창 닫기·로그아웃에서는 입력을 모두 비운다. 좁은 화면에서는 행 안의 항목을 세로로 배치한다.
- 전체 저장소 버전으로 동시 편집 충돌을 검사한다. 실패한 변경은 값과 버전·감사 기록을 함께 보존한다. 충돌 후에는 목록을 다시 불러오고 값을 새로 입력한다.
- 변경 감사 기록에는 키와 작업 종류(`created`, `updated`, `deleted`)만 남긴다. 이전 값·새 값은 기록하지 않는다.

## 워크플로우 참조

HTTP 헤더 값과 요청 본문에서 `{{vault.monitoring_api_token}}`처럼 참조한다. JSON 본문에는 `{"$path":"vault.monitoring_api_token"}`도 사용할 수 있다. 예를 들어 Authorization 헤더 값은 `Bearer {{vault.monitoring_api_token}}`이다. URL·조건·검색·날짜 입력·종료 메시지에서는 직접 참조할 수 없다. 일반 컨텍스트 주입 값은 비밀 값 저장소가 아니며 정의와 교환 JSON에 포함된다.

각 HTTP 시도는 전송 직전에 현재 서버의 값을 읽는다. 같은 실행의 다음 요청과 재시도에도 교체·삭제를 반영한다. 참조가 없는 분기는 값을 요구하지 않는다. 이미 전송한 요청은 이후 값 변경으로 취소되지 않는다. 값 안의 템플릿은 다시 해석하지 않는다.

키 누락·값 미설정·저장소 잠김·읽기 또는 복호화 실패 시 해당 HTTP 요청을 보내지 않고 실행을 실패 처리한다. 키 누락 오류에는 `vault.키`를 표시한다. 빈 문자열·기본값·기존 값으로 대체하지 않으며 HTTP 통신 오류 재시도나 계속 진행·오류 분기를 적용하지 않는다. 요청 전 참조 오류의 시도 상태는 `not-sent`다.

워크플로우 정의·실행 정의에는 참조만 저장한다. 사용한 비밀 값은 실행 출력·오류에서 가리며 실행 이력이나 감사 로그에 복사하지 않는다. API가 되돌려 준 원문 값도 가린다. 응답의 숫자·불리언·null은 문자열 표현이 비밀 값과 정확히 일치하면 저장 전에 가리고, 일치하지 않는 값의 자료형은 유지한다. 중첩 객체·배열에도 같은 규칙을 적용하며 후속 노드의 계산에는 원래 응답을 사용한다. 외부 API가 값을 임의로 변형한 결과까지 비밀 값으로 자동 판별하는 기능은 없다. 외부 호출의 대상과 전달 내용은 작성자가 관리한다.

Dry-Run은 실제 비밀 값을 읽지 않고 `[가림]`으로 요청을 조립하며 해당 노드의 `vaultKeys`를 결과에 표시한다. 키가 없는 서버에서도 흐름을 모의 실행할 수 있다. Dry-Run 성공은 실제 키 설정·인증 성공을 보장하지 않는다.

워크플로우 JSON에는 참조와 자동 산출한 `requiredVaultKeys`만 포함한다. 가져올 때 목록은 정의의 참조와 정확히 일치해야 한다. 다른 서버에서는 그 서버의 비밀 값을 별도로 등록해야 실제 호출할 수 있다. 기존 워크플로우별 `secrets`는 별개의 호환 기능이며 자동 대체하지 않는다.

## 백업과 초기화

현재 지원하는 schema 5의 이전 저장소에는 `secretStore`가 없어도 정상적으로 잠금 해제한다. 날짜별 저장소와 이전 단일 파일 저장소 모두 기존 이벤트·워크플로우·비밀 변수를 유지한다. 최초 비밀 값 등록 시 새 필드를 추가하고 다음 시작에서도 읽는다. 지원하지 않는 schema와 실제로 손상된 데이터의 오류 처리는 유지한다. 이 호환 범위는 이전 버전에서 현재 버전으로의 업데이트이며, 현재 데이터를 이전 앱으로 다시 저장하는 다운그레이드는 포함하지 않는다.

Danger Zone의 **전체 데이터 내보내기**는 비밀 값 저장소를 포함한 복호화 ZIP이다. ZIP과 임시 파일에는 실제 값이 포함되며 파일 자체는 암호화하지 않는다. 비밀번호·암호화 키는 포함하지 않는다. [내보내기·복원 절차](data-transfer.md)에 따라 보관하고, 운영자가 복사하는 암호화 데이터 백업에는 저장소 파일과 필수 관리 파일을 함께 보관한다.

전체 복원은 현재 비밀번호로 비밀 값 저장소도 함께 교체하고 편집 버전을 새로 발급한다. 비밀 값 저장소가 없는 기존 ZIP을 복원하면 빈 목록이 된다. 워크플로우 삭제·워크플로우 초기화·이벤트 초기화·감사 로그 초기화에서는 비밀 값을 유지한다. 시스템 전체 초기화에서는 함께 삭제한다.

## 인증 API

인증과 쓰기 Origin 검증은 다른 설정 API와 같다.

| API | 계약 |
| --- | --- |
| `GET /api/settings/vault` | `{ version, keys: [{ key, configured: true }] }`. 빈 저장소의 version은 0 |
| `PUT /api/settings/vault` | `{ version, key, value }`. 문자열은 등록·교체, null은 삭제. 응답은 목록과 새 버전 |

값을 반환하는 조회 API는 없다. 버전 충돌은 409, 없는 키 삭제는 404, 잘못된 키·값과 등록 개수 초과는 400이다.
