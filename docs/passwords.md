# 비밀번호 정책

## 신규 설정

웹 최초 설정과 시작 암호를 이용한 새 저장소 설정에는 같은 정책을 적용한다. 시스템 전체 초기화 후 다시 설정할 때도 신규 정책을 적용한다.

- 길이는 15~256자다.
- 허용 범위는 출력 가능한 ASCII `U+0021`(`!`)부터 `U+007E`(`~`)까지다. 영문 대소문자·숫자·특수문자를 허용하며 문자 종류를 반드시 섞도록 강제하지 않는다.
- 모든 공백과 제어 문자, 한글·전각 문자·이모지·결합 문자 등 ASCII 밖의 문자는 허용하지 않는다. 공백만 있는 값도 거부한다.
- 앞뒤 공백 제거·대소문자 변환·Unicode 정규화·문자 삭제·길이 잘라내기를 하지 않는다. 부적합한 값은 오류로 안내하고 다시 입력받는다.
- 부적합한 신규 암호로 안내문·암호화 저장소·설정 완료 파일을 만들거나 변경하지 않는다.

웹 화면과 서버는 `public/password-spec.js`의 규칙을 사용한다. 서버 검증은 화면을 거치지 않는 API 요청과 실행 인자의 최초 설정에도 적용한다. 비밀번호 허용 문자 검증은 워크플로우의 비밀 값 저장소에는 적용하지 않는다.

## 기존 저장소 호환

이미 설정된 비밀번호에는 신규 문자·길이 제한을 소급 적용하지 않는다. 로그인·시작 잠금 해제·복원 및 초기화의 암호 재확인은 기존의 12~256 UTF-16 코드 단위 범위와 키 도출 방식을 유지한다. 기존의 공백·Unicode·제어 문자가 포함된 값도 원문으로 검증하며 새 암호를 강제하거나 데이터를 다시 암호화하지 않는다.

실행 인자나 파일을 읽는 단계에서 신규 설정 규칙으로 값을 거부하지 않는다. 현재 저장소 상태를 확인한 뒤 실제 새 저장소의 설정에만 신규 정책을 적용한다. 실패 시 공백 제거·정규화 등으로 다른 후보를 만들어 재시도하지 않는다.

입력 경로 자체의 표현 범위는 유지한다. 암호 파일은 BOM 없는 한 줄 UTF-8 텍스트이며 마지막 LF 또는 CRLF 하나만 파일 구분자로 허용한다. 기존 암호의 앞뒤 공백과 Unicode는 그대로 보존하지만 파일 안의 NUL·내부 개행·잘못된 UTF-8은 허용하지 않는다. 구형 암호가 파일이나 OS 실행 인자로 표현되지 않으면 JSON API 등 원문을 전달할 수 있는 경로를 사용해야 한다. 브라우저의 비밀번호 입력란도 개행을 직접 표현하지 못한다.

## 실행 인자

두 인자 형식과 `=` 형식을 지원한다. 비밀번호 안의 `=`는 값의 일부로 보존한다.

```sh
node server.mjs --unlock-password '--valid-startup-password-2026'
node server.mjs --unlock-password='--valid-startup-password-2026'
node server.mjs --unlock-password-file=/var/lib/service-timeline/secrets/unlock-password
```

비밀번호가 옵션 이름 자체와 같은 경우에는 `--unlock-password=--unlock-password-file`처럼 `=` 형식을 사용한다. `--unlock-password --unlock-password-file`은 값 누락으로 거부한다. 옵션의 동시 사용·중복 지정·추가 인자는 형식에 관계없이 오류다. 암호 파일·권한·실패 처리와 wrapper 전달 방식은 [배포 안내](deployment.md#시작-암호로-백그라운드-준비)를 따른다.
