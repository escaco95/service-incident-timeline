# 워크플로우 작성·연동 지원 계획

작성일: 2026-09-10. 이 문서는 구현 전에 작성한 검토 계획이다. 현재 제공하는 기능·파일 규격·실행 명령·제한은 [JSON 작성 및 연동 안내](workflow-authoring.md)를 기준으로 한다.

## 확인한 요청과 검토 당시 기준

- [LANTERN 기능 요청 및 연동 원칙 정정](https://github.com/escaco95/service-incident-timeline/issues/1#issuecomment-5609013832): 서비스 유효 상태 변경 트리거가 최우선이다. 서비스 문자열과 프로젝트의 심각도 값으로 분기하며, 이전 커넥터 계약과 연동 전용 ID·정책·메타데이터 요구는 철회했다.
- [LANTERN Windows 테스트 실패 상세](https://github.com/escaco95/service-incident-timeline/issues/1#issuecomment-5609124049): `f050753ab3a3f08a951deb7e1a90eccd4ad3263a`, Node.js 22.23.1에서 전체 85개 중 5개, workflow 단독 9개 중 3개 실패했다. 백업 교체의 `EPERM`, 실행 결과 불일치, 완료 대기 실패의 인과관계는 미확정이다.
- 사용자 제안: AI가 화면에서 노드를 직접 조작하는 작업 대신 스크립트 또는 JSON 업로드·다운로드를 지원하고, 워크플로우당 100개 노드 예산으로 실행 구조를 단순하게 유지한다.

검토 당시 구현은 `f050753`의 사용 안내를 기준으로 했다. `lib/workflow-definition.mjs`와 `public/workflow-ui.js`에 노드 30개 제한이 각각 있었으며 연결은 60개였다. 워크플로우 개수 제한 100개와 구분해야 한다.

`lib/workflow-engine.mjs`는 이미 비동기 HTTP와 실행 큐를 사용한다. 한 실행은 분기 결과에 따라 한 경로를 순차 진행하며, 전체 동시 실행 2개·같은 workflow 1개, 전체 실행 120초, HTTP 시도당 최대 30초, 응답당 128KiB 제한이 있다. 별도 워커·분산 큐·병렬 그래프 실행기는 현재 요구의 선행 조건이 아니다.

## 권장 방향

**버전이 있는 workflow JSON을 공통 작성·교환 형식으로 정하고, 기존 화면과 실행기가 같은 정의를 사용하도록 한다.** 사내 에이전트는 파일을 생성·수정·검증하고, 운영자는 업로드한 정의를 노드 화면과 변경 비교에서 확인한다.

1. JSON 파일 업로드·다운로드, 스키마, 실행 없는 CLI 검증, 가상 예제를 먼저 제공한다.
2. 서버·화면·파일 검증의 노드 제한을 모두 100개로 맞춘다. 순환·병렬 분기는 계속 지원하지 않는다.
3. 서비스 유효 상태 변경 트리거와 실제 연동에 필요한 최소 데이터 처리 기능을 제공한다.
4. 서비스별 호출 순서·불명 결과 보류·기록 정책을 갖춘 뒤 실제 변경 API 연동을 검증한다.
5. 텍스트 문법의 필요성이 확인되면 같은 JSON으로 컴파일하는 선언형 DSL을 추가한다. 별도 실행 의미나 임의 JavaScript 실행 환경은 첫 범위에 넣지 않는다.

JSON은 작성 부담을 줄이지만 집계·날짜 변환·배열 검색 같은 실행 기능을 대신하지 않는다. 100개 노드도 외부 호출의 지연이나 적용 여부 불명 문제를 해결하는 제한은 아니다.

## 1. 저장 안정성 확인

먼저 다음 기준으로 사내 실패 보고를 좁힌다.

- 보고된 커밋의 격리된 작업본에서 Windows / Node.js 22.23.1과 현재 사용 중인 24.13.1을 비교한다. workflow 단독과 전체 테스트를 구분하고, 실패한 실행의 상태·노드·시도·안전한 오류 요약 및 실행기 fault를 함께 수집한다.
- `Vault.serialize()`로 같은 인스턴스의 변경은 이미 직렬화된다. `Vault.write()`의 백업·본 파일 교체, 다른 파일 접근 경로, 동시 테스트, 외부 파일 잠금 가능성을 확인한다. `EPERM`만으로 내부 쓰기 경합이나 보안 프로그램을 원인으로 확정하지 않는다.
- 일시적인 교체 실패로 확인되면 동일한 커밋 단계에서만 횟수·시간이 제한된 파일 작업 재시도를 검토한다. 원본·백업을 먼저 지우는 우회나 HTTP 재전송으로 대응하지 않는다.
- 호출 전 기록 실패 시 호출하지 않고, 호출 후 기록 실패 시 후속 호출을 멈추는 보장을 유지한다. 두 파일 교체 단계와 재시작 복구에 실패를 주입해 확인한다.
- `settle()`의 짧은 대기 상한과 실제 엔진 실패를 구분한다. 실패 출력을 보강하고 실제 저장·실행 문제를 조사한 뒤 필요한 경우 대기 방식을 개선한다. 기대 결과나 저장 실패 검증을 완화하지 않는다.

완료 기준: 보고 환경의 결과·재현 여부를 명시하고, 확인한 원인에 대한 회귀 검증과 호출 전후 저장 실패 검증을 통과한다. 전체 테스트는 이 단계의 구현 완료 시 실행한다.

이번 계획 수립 중에는 Windows / Node.js 24.13.1에서 다음 명령의 **16개 테스트가 모두 통과**했다.

```sh
node --test --test-reporter=spec test/workflows.test.mjs test/reset.test.mjs
```

이 결과는 `f050753`를 HEAD로 하는 기존 미커밋 변경 포함 작업본 기준이다. Node.js 22.23.1, 보고 커밋의 깨끗한 작업본, 전체 테스트, 브라우저·macOS·실제 업무 API를 이번에 검증한 것은 아니므로 사내 오류의 해결 근거로 사용하지 않는다.

## 2. JSON 작성·교환과 100개 노드 지원

교환 파일의 제안 구조는 다음과 같다. 이 예시는 기존 cron·종료 기능만 사용한다. 신규 트리거와 연산의 필드명은 별도 스키마 작업에서 확정한다.

```json
{
  "format": "service-incident-timeline/workflow",
  "formatVersion": 1,
  "definition": {
    "name": "가상 예제",
    "nodes": [
      {
        "id": "schedule",
        "type": "cron",
        "name": "일정",
        "config": { "expression": "0 9 * * 1-5", "timezone": "Asia/Seoul" }
      },
      {
        "id": "done",
        "type": "finish",
        "name": "종료",
        "config": { "result": "success", "message": "" }
      }
    ],
    "edges": [
      { "id": "schedule-done", "from": "schedule", "to": "done", "port": "next" }
    ]
  },
  "requiredSecrets": []
}
```

- `formatVersion`은 파일 형식 버전이다. 저장 충돌용 `version`·실행 정의의 `definitionVersion`과 구분한다. 지원하지 않는 버전·노드·설정 필드는 위치를 포함한 오류로 거부한다.
- 노드 ID는 사람이 읽을 수 있는 안정된 문자열을 사용한다. 파일의 좌표는 선택 사항으로 하고, 없으면 결정적인 자동 배치를 적용한다. 다운로드 시 좌표를 보존해 재업로드할 수 있다. 현재 좌표 필수 검증 앞에 정규화 단계를 추가한다.
- 서버 내부 workflow ID·활성 상태·실행 이력·비밀 값은 교환 파일에 넣지 않는다. 비밀 값은 기존 secret 참조로 표현하고 필요한 이름만 제공한다. 인라인 인증 값이 발견되면 참조로 옮기도록 오류를 제공한다. 임의 본문 속 비밀을 완전히 탐지할 수 있다고 보장하지 않는다.
- 새 파일은 검증·미리보기 후 OFF 초안으로 생성한다. 기존 정의에 적용할 때는 대상·현재 버전과 변경 내용을 확인하고 명시적으로 저장한다. 업로드 자체가 실행·활성화를 발생시키지 않는다.
- 다운로드는 저장된 정의를 기준으로 제공하고 편집 중 변경이 있을 때 이를 표시한다. 비밀 참조 이름과 `requiredSecrets`의 누락·불일치를 검사한다.
- 스키마뿐 아니라 순환, 연결점 중복, 트리거 수, 도달 가능성, 변수 경로, 가능한 실행 경로의 예산도 검증한다. 초안 저장 가능 여부와 실제 실행 가능 여부를 구분한다.
- CLI는 같은 검증·정규화 모듈을 사용하고 구조화된 오류와 종료 코드를 반환한다. HTTP 호출 없이 파일을 검증할 수 있게 한다. 로컬 HTTP fixture를 사용하는 연동 예제는 별도 명령으로 구분한다.
- 범용 조건에서 연결 없는 경로를 성공 종료하는 기존 동작은 명시한다. 서비스 연동 예제의 미일치·오류·검증 실패 분기는 반드시 명시적인 종료 또는 확인 필요로 연결한다.

제안 산출물: `schemas/workflow-file-v1.schema.json`, `lib/workflow-file.mjs`, `scripts/workflow-validate.mjs`, `examples/workflows/`, 파일 입출력 UI와 인증된 검증·다운로드 API. 실제 API 경로는 구현 시 기존 생성·저장 API와 맞춰 확정한다.

검증 기준: 다운로드→검증→업로드의 의미 보존, 좌표 없는 파일의 배치, 99·100개 허용과 101개 거부, 잘못된 버전·분기·변수의 오류 위치, 비밀 값 제외, OFF 생성, 기존 정의의 버전 충돌, 100개 노드 화면 조작을 확인한다. 기존 UI의 편집 초안·세션·저장 충돌 동작을 재사용한다.

## 3. 서비스 유효 상태 변경 트리거

- 이벤트의 선택 항목 `services[].label`을 정확한 문자열로 비교한다. `event.service`는 호환용 표시 문자열이므로 복수 서비스 집계의 원본으로 사용하지 않는다. 같은 label의 catalog/custom 항목은 이 트리거에서 같은 대상으로 취급하며 한 이벤트에서 중복 집계하지 않는다. 다른 ID라도 같은 문자열이면 구별할 수 없다는 요청의 전제를 문서화한다.
- 평가 시각에 `start <= now`이고 `end === null || now < end`인 이벤트 전체로 서비스별 상태를 계산한다. 화면에서 조회한 기간이나 필터를 집계 범위로 사용하지 않는다.
- 기존 `public/date-utils.js`의 심각도 규칙은 장애가 있으면 `incident`, 그 외 이벤트가 있으면 `warning`, 없으면 빈 문자열이다. 이벤트의 `category: maintenance`와 집계 결과 `warning`을 구분하고 이 규칙을 서버와 공유한다. 별도 연동 전용 상태 ID나 우선순위 정책을 만들지 않는다.
- 같은 평가 시각의 시작·종료를 함께 반영한다. `정상 → 황색 → 적색 → 황색 → 정상`에서 실제 결과가 바뀐 서비스에만 실행을 접수한다. 근거 이벤트만 바뀌면 근거 기록만 갱신한다.
- 시작·종료뿐 아니라 이벤트 생성·수정·삭제와 서비스 선택 변경을 반영한다. 아직 없는 취소 모델을 새로 가정하지 않는다. 변경 저장 후 재평가가 중단되어도 주기적 확인으로 누락을 복구한다.
- 날짜별 저장의 기간 색인을 사용해 현재 활성 이벤트와 종료 미정 이벤트를 포함한다. 현재 시작·종료 트리거의 짧은 시간 범위 조회만 재사용하면 오래전에 시작한 이벤트를 놓칠 수 있으므로 별도 활성 범위 조회가 필요하다.
- 마지막 계산 상태와 대응하는 실행 접수를 같은 저장 단위로 확정한다. 일반 감사 이력의 보관 만료로 상태 기준점·미완료 보류·접수 중복 방지 정보가 사라지지 않게 한다.
- 최초 도입은 현재 상태를 기준점으로 저장하고 자동 변경 호출은 하지 않는 방안을 기본으로 제안한다. 최초 외부 동기화는 명시적인 현재 상태 평가 동작으로 제공한다. 재시작·잠금 해제는 마지막 기준점과 현재 상태를 비교하며 지나간 상태를 차례로 재생하지 않는다. 기준점이 없으면 초기 수립 규칙을 적용한다.
- 입력에는 서비스 문자열·이전/현재 심각도·평가 기준 시각·최소 근거 이벤트 참조를 제공한다. 실행과 노드 추적은 기존 기록을 확장한다. 연동을 위해 새로운 대상 ID 체계를 도입하지 않는다.

검증 기준: 동급 중첩, 적색 동안의 황색 변화, 동일 시각 경계, 복수 서비스의 일부만 변경, 마지막 이벤트 삭제, 진행 중 이벤트의 서비스 문자열 변경, 최초 도입, 중단 중 여러 변화, 잠금 해제, 근거만 변경, 저장 실패 후 재평가를 가상 데이터로 확인한다.

## 4. 최소 데이터 처리 기능

| 기능 | 첫 제공 범위 | 완료 검증 |
| --- | --- | --- |
| 조건 | 고정값/경로 간 비교, AND/OR, 엄격한 자료형 비교, null·누락 구분 | 이전·이후 응답의 여러 필드 비교, 누락·null·빈 문자열·0·false |
| 목록 검색 | 키 조건으로 찾고 0건·1건·복수 건을 명시적으로 분기 | 배열 순서 변경, 중복 키, 배열 아님, 자료형 불일치 |
| 시각 | 트리거 기준 시각, 노드 실행 시 현재 시각, 시간대·형식 변환 | UTC/Asia/Seoul, 날짜 경계, 지연 실행, 동일 실행 안의 재사용 |
| JSON 값 삽입 | 경로 참조의 숫자·불리언·객체 자료형 보존 | 현재 문자열 템플릿과 호환되며 이중 인코딩·유효하지 않은 JSON 방지 |

범용 데이터 연산의 크기·연산 횟수에도 상한을 둔다. 시각은 트리거 기준값을 실행 입력에 고정하고, 적용 직전 현재 시각은 해당 노드가 실행될 때 평가한다. 다시 실행은 과거 입력 재사용과 현재 목표 재평가 중 어떤 동작인지 구분한다. 전체 배열 반복·하위 workflow·범용 코드 노드는 후순위다.

## 5. 순차 실행을 유지하면서 필요한 실행 보장

100개 노드 제한과 별개로 다음 기능은 실제 상태 변경 연동의 완료 조건이다.

- 같은 서비스 문자열은 workflow가 달라도 하나씩 실행한다. 서비스 변경 트리거의 실행에는 자동으로 서비스 실행 키를 연결하고, 수동·cron 흐름이 같은 서비스를 변경한다면 해당 서비스 문맥을 명시하도록 한다. 대상이 선언되지 않은 임의 HTTP 흐름까지 자동으로 동일 대상으로 인식한다고 주장하지 않는다.
- 서비스 실행 키를 확보한 뒤, 실제 변경 HTTP 전송 직전에 최신 목표·정의·활성화·허용 범위를 다시 확인한다. 이미 오래된 대기 작업은 생략하고 최신 상태를 재평가한다. 결과가 불명인 기존 호출이 있으면 새 변경을 보류한다.
- HTTP의 조회/변경 의도를 범용 설정으로 구분한다. 메서드만으로 판단하지 않는다. 변경 호출은 기본 재시도 0회이며 외부 중복 방지가 확인되지 않은 설정에서 자동 반복을 허용하지 않는다.
- 변경 요청 후 timeout·응답 유실·결과 저장 실패·재시작 시 미완료 호출은 미적용 실패로 확정하지 않는다. `확인 필요`와 서비스 보류를 영속화한다. 초기에 자동 조회 대기는 제공하지 않아도 되지만 불명 결과 보류는 필요하다.
- 결과 확인·현재 상태 재검증·수동 해소는 별도 동작과 감사 기록으로 남긴다. 단순히 현재 상태가 같다는 이유만으로 늦게 완료될 이전 요청이 끝났다고 판단하지 않는다. 해소 후 최신 목표를 재평가한다.
- 현재의 ‘같은 버전·입력으로 처음부터 다시 실행’은 유지하되, 최신 상태 재평가·실패 지점의 재시도·결과 확인과 화면/API에서 구분한다. 이전 성공 호출의 자동 반복을 피하고 기존 실행·시도 관계를 남긴다.
- 조건 계산용 전체 응답과 저장용 출력을 분리한다. 본문 미저장 또는 출력 필드 허용 목록을 제공하고, 기존 비밀 가림은 추가로 적용한다. 저장 전 단계부터 이 정책을 적용한다.

검증 기준: 서로 다른 workflow의 동일 서비스 호출, 대기 중 목표 변경, 전송 직전 비활성화, 응답 유실 후 다음 변경 보류, 조회와 변경의 분리, 중복 요청, 재시작·수동 해소 이력 연결, 미허용 본문 필드 미저장을 확인한다.

## 실행 예산과 용량

| 항목 | 제안 | 이유·확인 사항 |
| --- | --- | --- |
| 정의당 노드 | 100개, 트리거·종료·데이터 처리 포함 | 실제 선택 경로도 최대 100단계이며 순환은 거부 |
| 정의당 연결 | 최대 200개, 현재 노드의 출력점 규칙 유지 | 조건·오류 분기를 포함하되 출력점당 다음 노드 하나 |
| HTTP 시도 | 실행당 최대 100회 제안, 재시도 포함 | 가능한 경로별 최대치를 사전 계산하고 실행 중에도 집계 |
| 실행 시간 | 우선 기존 120초 유지 | 노드 수와 별도 제한. 상향은 모의 부하 측정 뒤 결정 |
| HTTP·응답 | 기존 시도당 최대 30초·응답당 128KiB 유지 | 100개 노드가 긴 외부 대기 100회를 허용한다는 뜻은 아님 |
| 정의 파일 | 우선 1MiB 상한 제안 | 현재 공통 JSON 요청 상한은 256KiB. workflow 경로에 한정해 조정하고 CLI/UI/API를 일치시킴 |
| 동시 실행 | 기존 전체 2개 유지 + 서비스별 직렬화 | 추가 워커나 병렬 그래프 없이 먼저 검증 |

예를 들어 한 경로에서 HTTP 20회가 각각 3초라면 네트워크 대기만 60초이고, 50회면 150초다. 따라서 100개 노드만으로 처리 가능성을 보장할 수는 없다. 다만 다수의 조건 분기는 한 실행에서 모두 거치지 않으므로 서비스·상태별 고정 분기에는 유용한 예산이다.

현재 실행기는 노드 시작·완료와 HTTP 시도 시작·완료마다 저장한다. 100단계에서 저장 지연, 누적 출력과 정의 스냅샷의 복제·암호화 비용, 날짜별 이력 크기를 측정한다. 호출 전 기록을 생략해 속도를 맞추지 않는다. 파일당 상한뿐 아니라 기존 저장 파일 64MiB 한도와 여러 workflow·실행 이력이 함께 차지하는 총량도 검사한다.

20·60·100개 노드의 조건 중심 및 HTTP 중심 예제로 경로 길이·시도 횟수·전체 시간·대기열 지연·저장 크기와 화면 응답을 기록한다. 서비스별 실행 유입률이 순차 처리량을 넘거나 수분 이상의 조회 대기가 실제로 필요해지는 시점에만 영속 대기·체크포인트 재개·추가 워커를 후속 설계한다.

## 전달 순서와 역할

1. **진단 기준 확보:** 사내 실패 재현·저장 안정성 및 안전한 오류 출력.
2. **작성 지원 전달:** JSON 스키마·CLI·파일 입출력·100개 노드·기본 가상 예제. 서비스 트리거 완성 전에도 기존 start/end/cron으로 사내 파일 작성 작업을 시작할 수 있다.
3. **기능 연결:** 서비스 상태 집계·변경 트리거와 최소 조건·검색·시각 처리.
4. **운영 연동 완료:** 서비스별 직렬화·최신 상태 확인·불명 결과 보류·기록 정책과 통합 검증. 실제 변경 API 연결은 이 조건을 충족한 뒤 진행한다.

공개 프로젝트는 범용 실행 기능, 파일 규격, 검증 도구, 가상 예제와 회귀 검증을 담당한다. 사내 에이전트는 서비스 문자열·제공 심각도에 대한 조건 및 실제 URL·요청·응답 판정·secret 공급을 자기 배포의 JSON으로 구성한다. 공개 문서·fixture에는 실제 업무 데이터와 인증 값을 넣지 않는다.

각 전달 단위에 지원 범위·실행 명령·검증 환경·미검증 범위를 기록한다. 독자 DSL, 병렬 실행, 반복, 하위 workflow, 자동 장기 폴링은 첫 전달의 선행 작업으로 두지 않는다.
